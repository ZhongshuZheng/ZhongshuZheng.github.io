# Design Principle

*创建时间：2024-08-01*

一般的 MVC 是贫血模型，既数据与方法完全区隔开；将 controllor 的方法和数据按照所属分配，是充血模型。

## SOLID 原则

- **S-single**：一个模块只处理一种任务。
- **O-openclose**：好设计接受扩展，不接受修改。“修改”指的是改了新功能，旧功能可能会需要重新单元测试。
- **L-Lsp**：子类必须正确实现父类所能适应的所有场景。
- **I-interface**：接口隔离，类似于 S，一个接口（interface 类）只干一件完整的事情。
- **D-dependency inversion**：设计模块依赖于某个固定的抽象，而不要依赖于具体的实现，如 OJ 上面题的答题框架，通过参数传进来，而不是 new 一个。

## 其他原则

- **KISS 原则**：简单实现，易于阅读。
- **Yagni**：奥坎姆剃刀。
- **DRY**：别重复。
- **LOD**：迪米特法则，模块间不该依赖的不要互相依赖。例如：超市买东西，给售货员钱，而不是钱包；最简单的实现，给不同的调用方使用的东西，不要写在一个类中。

## 重构的内容

- **大重构**：通过设计原则与模式，分层，模块化，解耦，抽象化可复用部分。
- **小重构**：命名，注释，超大类拆解，抽取重复函数。

## 单元测试

对于外部服务，mock 一下；静态方法/全局变量 mock 比较复杂，较难测试，要注意控制，除非是不存在未决行为的函数，否则不要写成 static 或全局！

## 代码质量

- 符合设计原则 solid，dry，kiss，lod，yagni
- 设计模式是否合适 or 过度
- 易用：配置修改，调用，是否简单？
- 可扩展：能否切换各种不同的算法，数据源
- 可复用
- 可测试
- 可读

## 高级问题检查

- 逻辑正确
- 日志合适
- 并发安全，线程安全：如执行过程中调整数据源是否会有影响
- 性能优化：延迟，是否需池化
- 容错：如果依赖的服务崩了，能否兜底

## 进行面向对象思维设计的入口

把所有的具体对象，系统的业务功能，可执行算法，作为独立的类，围绕这些类进行模式设计，这些功能与算法类；同时由于迪米特法则，通常也会配套输入与输出的数据类。这样，基本符合了 solid 与其他各种设计原则。

### 举个例子

实现排序功能（或某独立的单元逻辑），要支持多种排序算法，每种排序算法的需求输入输出各有轻微不同。那么所有算法继承一个 sort base 类，该类实现 execute 接口，接口接纳 input base 类，输出 output base 类，然后每个算法自己实现自己的输入输出类。

### 原因

- 为什么不能直接对接口写参数？会导致该接口无法拓展容纳更多的算法。
- 为什么不直接给一个 dict？正常来说可以，不过如果算法间输入输出可复用性高，还是抽象成一个更易复用。
