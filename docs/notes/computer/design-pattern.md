# Design Pattern

*创建时间：2017-05-08*

> 复杂度不会消失，只会转移。

设计模式的定义分为面对的问题与解决方案。在解决方案上，很多模式是一样的，只不过面对问题的角度不同，比如策略模式、命令模式、职责链模式。

## 创造器类

### Factory

不同对象的生成：把常变动的生成部分抽象在一起，如用工厂来生产一些有着不同但固定配方的药水。

- 用于面对创建对象逻辑复杂的场景。
- **简单工厂**：通过 If 判断，返回对应的类。问题是每次增加新的东西，都需要改动这个大工厂。
- **工厂方法**：把生产组装的部分设计成工厂类，不同的类由不同的工厂产生，并且通过一个统一的工厂选择并调用这些“小”工厂。这样，新的类只需要增加新的小工厂，并在大工厂增加一条 If 之类的逻辑。
- **抽象工厂**：（不太重要）把小工厂写成接口，让中工厂组合小工厂；提供创建一组相关产品的接口，而不直接依赖具体产品类。
- **DI 容器（依赖注入容器）**：通过编写 XML 配置和反射，实现外部动态构建类。

### 建造者模式

用来隔绝对象修改接口：自定义构造需求的一个静态内部类。这个内部类可以访问对象的全部特征，并且对象必须由这个类进行初始化，所有构造需要的参数先传给这个静态类。

- 目的是避免构造函数过长或过于复杂。
- 与工厂模式很像，但工厂模式的目的是构造结构相似、功能不同的类；建造者模式只是用来抽象构造函数，封装参数初始化的接口。
- 具体来说，工厂模式直接根据参数给出产品；而建造者模式会提供大量不同参数的接口，按需调用实现创建。

使用建造者模式创建状态：

```gdscript
func create_unit_selected_state(unit: BattleUnitBase) -> void:
    var state = BattleStateBuilder.new() \
        .build_state(BattleUnitSelectedState) \
        .with_unit(unit) \
        .with_target(target) \
        .with_status(status) \
        .build()
    return state
```

### 单例模式

某些全局注册的场合需要。

- 用于处理资源共享冲突、全局独一份数据的问题。
- 需求：构造函数私有、线程安全、高性能。
- 饿汉式不能延迟加载。
- 懒汉式每次都加锁，性能差；创建时双重加锁有可能发生 CPU 重排。
- 问题：难以继承或多态，扩展性、测试性不好，不支持构造函数改动。
- 单例一般是进程唯一的。如果要线程唯一，可通过 HashMap 线程 ID 实现；如果要进程间唯一，即集群唯一，那只能通过外部存取加锁。

### 外观模式

接口太多、组合冗杂，接口间需要存在逻辑关系时，对相应的接口直接打个大包。

## 基本的接口抽象类

### Strategy

勇士的右手装备各种不同的武器。

- 通常通过工厂模式来组装，可以配合 Map 查表实现。

### 模板模式

把需要一连串执行的方法统一在一起，按需求顺序执行，然后提供抽象的方法接口。与策略模式挺像的，也是不需要多想、很自然会想到的一种实现模式。

### 桥接模式

说不上来，感觉有一丢丢丢像策略模式：把可能有多种选择组合的逻辑拆开，临时拼装使用。例如，3 种通知方法与 3 个通知紧急程度写成两个类，用时拼装。只不过策略模式有一个大东西做主体，桥接模式就两边接在一起。

## 维持核心不变的能力扩展类

### 代理模式

在原逻辑中加入相关附属逻辑时，如计时器、监控等，为避免“侵入性”代码，通过实现代理类来组合原业务逻辑和其他附属逻辑，保证原逻辑类的完整性。

- **静态代理**：通过和原类实现相同接口，或直接继承原类，在需要调用原方法时调用父类或原类的方法来代理执行。继承的好处在于不用为所有函数代理，但缺点也是继承。
- **动态代理**：通过反射机制动态获取对应类和方法，在执行方法前后加入其他逻辑。具体到对应语言的用法还得再看。

### Decorator

一瓶用来喝的药水被混合了数目不定、具有各种效果的草药；这些效果可能在药水生效前或生效后发生，但药水还是用来喝，内核不变。

- 实现类似代理模式，装饰器类和核心类都实现同一个核心接口。装饰器类前后做自己需要的工作，然后通过代理调用原核心逻辑。
- 与代理模式的区别在于，装饰器是修饰、强化核心功能，而代理模式是补充其他附属逻辑。

### 适配器模式

用来统合不同版本代码的接口。

- 可以基于继承或组合实现。基于继承就是继承旧类、实现新接口；基于组合就是实现新接口，定义旧类成员来调用。

## 不同功能但封装相同接口类

### Observer

触发器被各种响应函数订阅或取消订阅。

- 被订阅者自己维护订阅者名单，订阅同一个事件的订阅者统一实现同一个接口，以便被订阅者调用。

### 命令模式

实现上与策略模式基本一样，区别在于要求统一的 `execute` 接口，以便按某些顺序或随机执行。

- 命令模式的核心理解在于封装请求，策略自行执行。
- 与策略模式的区别在于，策略模式通过封装接口匹配用于同一位置的不同策略。两者实现上类似，理解上不同。

### 职责链模式

所有要执行的逻辑都实现一个 Handler，然后由一个外部类依序调用 Handler，就像 CarpoolScore 的 Filter 一样。

- 常用来实现过滤、拦截功能。
- 增减 Filter 可以通过外部文件配置、反射加载来提高灵活性。
- 优点是在不知道未来会出现哪些新业务逻辑时，可以有效封装、隔离当前业务，并为未来业务扩展提供接口。
- 与触发器模式的区别是，触发器是并行逻辑，职责链是串行逻辑。

## 框架类

### 迭代器模式

顾名思义，给集合设计通用迭代器，达到简化代码、迭代与存储分离、可使用不同迭代策略的目的。

- 迭代器接口需要实现 `has_next` 和 `next` 方法。
- 具体的迭代器类“组合”需要遍历的容器，“实现”迭代器接口。
- 迭代器存在增加或删除不可用的问题，可通过 Snapshot 解决，如 Deep Copy，或者类似数据库的时间戳来逻辑删除。

### 组合模式

面对树状或层级组织的数据时，可以通过树节点表示集合层级，比如菜单、DOM、文件系统，或 Unity 的底层实现。

- 抽象树节点类，所有单元类继承节点类。

### 状态模式

状态机的实现。每一个状态是一个子类，实现该状态下可以执行的动作以及状态转移，用于避免大量的 If-Else 判断。

- 可配合享元模式，将单位状态数据以及单位状态实现类分离。例如，每个单位具有一个状态数据 Context，同时有一个状态行为实现 State。State 指向享元状态；切换状态时，向 State 传入 Context 进行调整，之后将 State 指向新的状态。

## 节约资源类

### 原型模式

当新建一个对象资源消耗较大时，如 SQL、文件 I/O，直接 Copy 一个来避免重建。

### 享元模式

把需要大量生产的对象的可共享部分抽出来，每次提供外部状态来共享使用、节约资源，例如下棋游戏的棋子外形数据、文本编辑器的字体说明数据。

- 这些大量的对象由于数量巨大，即便里面只有几个 Int，也会带来大量内存占用。
- 享元与单例模式类似，只不过享元可以有多种，更类似于多例。不过意义不同：单例是为了限制个数，享元是为了共享数据。

### 对象池模式

池化。跟享元模式的区别是独占使用，用后解锁。

## 其他

### 访问者模式

不是很好用，能看懂就行。当存在多个接受不同子类作为参数的重载函数时，没法使用“父类”进行访问。解决方法是由父类定义一个“访问”接口，每个子类实现接口去调用重载函数。个人感觉完全可以用策略加工厂模式替代。

### 备忘录模式

用于快照或存储，可读档、悔棋。一个备忘录信息类用于记录关键信息；一个原始类实现生成或读取备忘录信息的接口；一个备忘录类用来持有并管理所有备忘录信息，可与原始类交互。

- 可作为游戏存档的实现方式。
- 悔棋这种存储量大的场景，可做增量保存。

### 解释器模式

用来处理某些文本命令，通过实现了解释接口的类进行翻译。场景不多，需要用到再学。

### 中介模式

中间层，意义不大。
